1 Is the Generated Sitemap XML Committed to the Git Repo?

There are three feed artifacts in this project. Each has a different generation and storage mechanism.

1.1 /sitemap.xml — Standard Page Sitemap
AttributeDetail
Committed to Git?❌ No
GenerationPlatform-generated at runtime by AEM EDS
Source data/query-index.json (built by the EDS indexing pipeline)
Config fileshelix-query.yaml, helix-sitemap.yaml

helix-sitemap.yaml instructs the EDS platform to read query-index.json and serve /sitemap.xml dynamically. No file is ever written to the repository.

# helix-sitemap.yaml
sitemaps:
  aig-eds-migration-poc:
    source: /query-index.json
    destination: /sitemap.xml
    lastmod: YYYY-MM-DD

helix-query.yaml defines the query-index that feeds it — indexing title, description, image, lastModified, robots, hidenav, and bodyText from every published page.

To verify: curl https://main--aig-eds-migration-poc--kprasad05.aem.live/sitemap.xml

1.2 video-sitemap.xml — Video Sitemap
AttributeDetail
Committed to Git?✅ Yes — file exists at repo root, tracked by Git
Generationtools/generate-video-sitemap.js (Node.js script)
TriggerDaily cron (0 6 * * * UTC) + manual workflow_dispatch
Workflow file.github/workflows/video-sitemap.yaml
Commit authorgithub-actions[bot]
Commit messagechore: update video-sitemap.xml

How data flows:

helix-query.yaml (video-index) │ ▼ /video-index.json (EDS index, live environment) │ ▼ tools/generate-video-sitemap.js │ fetches video-index.json │ filters rows where videourl is set │ builds Google Video Sitemap XML ▼ video-sitemap.xml ──► committed to main branch │ ▼ Served as static file: /video-sitemap.xml

Workflow commit logic:

- name: Commit if changed
  run: |
    git add video-sitemap.xml
    if ! git diff --cached --quiet -- video-sitemap.xml; then
      git config user.name "github-actions[bot]"
      git config user.email "github-actions[bot]@users.noreply.github.com"
      git commit -m "chore: update video-sitemap.xml"
      git push
    else
      echo "No changes to video-sitemap.xml"
    fi
⚠️
Known past bug (now fixed): The workflow originally ran git diff --quiet before staging, so a never-committed video-sitemap.xml always appeared unchanged. The fix stages first (git add), then diffs with --cached. Confirm this fix is merged before trusting the daily automation.

Currently committed content: 5 video entries (all under /drafts/), covering YouTube and direct .mp4 links.

3 How Does It Support Multi-Tenancy?

AEM EDS multi-tenancy is platform-native — encoded in the URL structure, not in any application-level tenant configuration within this repository.

EDS URL = Tenant Identity
https://{branch}--{site}--{org}.aem.live
                  ^^^^    ^^^
                  repo    GitHub org
SegmentThis ProjectRole
branchmainCode/content version
siteaig-eds-migration-pocThe tenant site (= repo name)
orgkprasad05GitHub organization/owner

Each org + site + branch combination maps to a completely isolated EDS environment with its own content index, platform-generated /sitemap.xml, and configuration files.

Multi-Tenancy Per Sitemap Type

/sitemap.xml (Platform-Generated)

  • Fully isolated per tenant by the EDS platform — each tenant has its own query-index.json.
  • No code changes needed; isolation is automatic.

video-sitemap.xml & article-really-simple-syndication.rss (Committed)

Generator scripts are tenant-configurable via CLI arg or env var:

node tools/generate-video-sitemap.js https://main--other-site--other-org.aem.live
# or: SITE_HOST=https://main--other-site--other-org.aem.live in the workflow
The One-Repo-Per-Tenant Model
kprasad05/aig-eds-migration-poc        other-org/other-site
  ├── helix-sitemap.yaml                 ├── helix-sitemap.yaml
  ├── helix-query.yaml                   ├── helix-query.yaml
  ├── video-sitemap.xml                  ├── video-sitemap.xml
  └── .github/workflows/                 └── .github/workflows/
  (tenant A)                             (tenant B)

Each tenant is a separate GitHub repository. Tenancy is achieved by the EDS platform's org + site + branch URL scheme — there is no runtime routing or tenant-selection logic in application code.

4 Will It Cause PR Merge Conflicts (Fast-Forward Not Allowed)?
⚠️
Yes — this is a real risk. The workflows push commits directly to main, bypassing PRs. Any in-flight PR will have a diverged history the moment a bot commit lands.
4.1 How the Conflict Arises
time ──►
main:           A ── B ── C  (developer PR merged)
                          └── bot commit D  (chore: update video-sitemap.xml)
feature-branch: A ── B ── X ── Y  (developer's in-flight PR)
ScenarioWhat Happens
Bot commits video-sitemap.xml while a PR also touches itHard merge conflict — Git cannot auto-resolve.
Bot commits while a PR does not touch itPR branch is behind main — may block merge if "Require branches to be up to date" is enforced.
Bot commits run when no PRs are openNo conflict — clean fast-forward is possible for the next PR.
4.2 Current Repo State
✅
No branch protection rules are currently configured. "Require linear history" and "Require branches to be up to date" are both not enforced. Direct pushes by github-actions[bot] are allowed.
FileBot commits it?Developer likely to touch it?Conflict Risk
video-sitemap.xml✅ DailyPossible (if manually regenerating)⚠️ Medium
article-really-simple-syndication.rss✅ DailyUnlikely🟢 Low
helix-sitemap.yaml❌ NoPossible (config changes)🟢 None from bot
helix-query.yaml❌ NoPossible (index changes)🟢 None from bot
4.3 Mitigations
  • Option A — .gitattributes merge strategy (recommended)

    Mark bot-committed files to always prefer the regenerated version on conflict:

    # .gitattributes
video-sitemap.xml                       merge=ours
article-really-simple-syndication.rss   merge=ours
  • Option B — Rebase-before-merge policy
    git fetch origin
git rebase origin/main
git push --force-with-lease

    Bot commits are small (chore: update ...) and trivial to rebase over.

  • Option C — Schedule bot off-peak

    Both workflows run at 0 6 * * * UTC (11:30 AM IST). Rescheduling to 0 0 * * * (05:30 AM IST, before the workday) reduces the overlap window.

  • Option D — Dedicated bot branch + auto-PR

    Push bot output to bot/update-video-sitemap and open a PR to main instead of pushing directly — keeps main clean but adds merge latency.

  • Option E — Scope branch protection to status checks only

    Require lint/build status checks to pass without requiring the branch to be fully up to date — allows merging even if the bot has pushed since branching.

4.4 Summary

Is "Require branches to be up to date" enforced?❌ No

5 Can Template and Publishdate Be Automated for the Article RSS Feed?

Yes — both fields can be partially or fully automated, depending on the authoring convention chosen.

5.1 Current State: Both Fields Are Manually Authored
FieldWhere It LivesHow It's Set
TemplatePage metadata (<meta name="template">)Author manually types Article Template in the metadata table
PublishdatePage metadata (<meta name="publishdate">)Author manually types a date string in the metadata table

The generator already has a fallback: if publishdate is absent it uses lastModified (the page's HTTP Last-Modified header). However lastModified drifts every time the page is re-published.

5.2 Automating Publishdate
ApproachAutomation LevelAccuracyEffort
lastModified fallback (current)✅ Auto⚠️ Drifts on re-publishAlready done
Date from URL path /articles/YYYY/MM/DD/slug✅ Fully auto✅ StableLow — URL convention + small code change
Admin API firstModified✅ Fully auto✅ Most accurateHigh — auth + per-page API call
Author-entered Publishdate (current)❌ Manual✅ Correct—

Best practical approach: adopt /articles/YYYY/MM/DD/slug URL convention and extract the date from the path in the generator:

function extractDateFromPath(rowPath) {
  const match = rowPath.match(/\/articles\/(\d{4})\/(\d{2})\/(\d{2})\//);
  return match ? `${match[1]}-${match[2]}-${match[3]}` : null;
}

function resolvePubDate(row) {
  if (row.publishdate) return toFeedDate(row.publishdate);        // explicit wins
  const pathDate = extractDateFromPath(row.path);
  if (pathDate) return toFeedDate(pathDate);                      // from URL
  if (row.lastModified) return toFeedDate(row.lastModified * 1000); // fallback
  return toFeedDate();
}

No changes to helix-query.yaml needed — publishdate remains as an optional override.

5.3 Automating Template
  • Option A — Use folder path alone (zero author input)

    Drop the template check: return row.path.startsWith('/articles/');
    Risk: non-article pages accidentally placed under /articles/ would appear in the feed.

  • Option B — Infer from URL date pattern

    return /^\/articles\/\d{4}\/\d{2}\/\d{2}\//.test(row.path);
    Date-in-URL is the implicit "this is an article" signal — no author action needed.

  • Option C — Pre-fill via Document Authoring Template ✅ Recommended

    In DA, pre-fill Template: Article Template in the Article template document. Authors get it automatically when creating a new article — they cannot forget or misspell it.

  • Option D — Replace template with a category field

    Add category: news to helix-query.yaml's article-index and filter on that instead — semantically richer, still pre-fillable in the authoring template.

5.4 Recommended Combined Approach
GoalRecommended ChangeEffort
Eliminate manual PublishdateAdopt /articles/YYYY/MM/DD/slug URL convention + extract date from path in generatorLow
Eliminate manual TemplatePre-fill Template: Article Template in the Article authoring template documentMinimal
Fully remove template dependencyDrop template check; rely on /articles/ folder + date URL patternLow
6 What Is the Body Selector Limitation of helix-shared-indexer (4.6.1)?
6.1 What Is It?

The body selector limitation is the fact that CSS selectors targeting the <main> body (or any element inside it) do not work in helix-query.yaml when the content source is AEM Sites (Universal Editor / BYOM).

The version reference 4.6.1 corresponds to a known behaviour in @adobe/helix-shared-indexer — the package the EDS platform uses internally to evaluate helix-query.yaml index expressions. In that version, body-scoped selectors are silently skipped (returning an empty string) for AEM Sites-sourced content, even when the YAML syntax is correct.

ℹ️
This was documented during work on the sibling project aig-aem-eds-poc (AEM Sites content source). docs/search.md in this project explicitly records that observation and explains why it does not apply here.
6.2 Why Does It Happen?
Content SourceHow Pages Are IndexedBody Selectors Work?
Google Drive / SharePoint / DA (this project) Indexer fetches the page's rendered .plain.html from the EDS CDN and runs selectors against that HTML ✅ Yes — main, main .video-feature a, etc. all resolve correctly
AEM Sites (Universal Editor / BYOM) Content is sourced via AEM's Page API; the indexer processes a metadata-only representation — no rendered body ❌ No — <main> and body-level elements are absent from the indexable HAST tree

The @adobe/helix-shared-indexer uses hast-util-select to evaluate selectors. The CSS syntax (main .video-feature a) is entirely valid — the problem is upstream: the HAST tree received for AEM Sites pages simply contains no main element to select from. No error is thrown; the column is silently empty.

6.3 Concrete Symptoms on the Sibling Project

Three separate attempts all returned empty strings in query-index.json:

# Attempt 1 — identical to what works in this repo
bodyText:
  select: main
  value: words(textContent(el), 0, 300)

# Attempt 2 — narrower selector
bodyText:
  select: main > div p
  value: textContent(el)

# Attempt 3 — selectFirst variant
bodyText:
  selectFirst: main p
  value: textContent(el)

The YAML syntax was never the problem — the same words(textContent(el), 0, 300) works correctly in this repo.

6.4 Why This Project Is NOT Affected

This project uses DA/git as the content source. The indexer fetches {path}.plain.html from the EDS CDN — a full rendered page with a real <main> element. Living proof:

# helix-query.yaml — these all produce populated columns here:
bodyText:
  select: main                         # full main content
  value: words(textContent(el), 0, 300)

videourl:
  select: main .video-feature a        # body-scoped selector works
  value: attribute(el, "href")

videothumbnail:
  select: main .video-feature img      # body-scoped selector works
  value: attribute(el, "src")

video-index.json has populated videourl and videothumbnail columns for pages with a video-feature block — confirming body selectors work.

6.5 Implications & Workarounds
SituationImpact
Project stays on DA/git content source✅ No limitation — body selectors work
Project migrates to AEM Sites⚠️ Breaks silently — bodyText, videourl, videothumbnail all go empty

If AEM Sites content source is adopted, body-indexed fields require one of:

  1. Store values in <head> metadata — surface body content as a meta tag via AEM page properties.
  2. Custom AEM servlet / GraphQL endpoint — query AEM's Lucene/Oak index server-side instead of query-index.json.
  3. AEP Data Collection — index page content via client-side collection at publish time, feeding Algolia or Elasticsearch.
  4. Hybrid approach — keep the metadata index for title/description/path; use a separate full-text index for body search. The search-results block already supports this pattern via Promise.allSettled.
